# 招商双债LOF择时体系运作流程

> 本文件是体系流程的唯一事实源。盘后任务的执行指引见**第 2 节**；任务 prompt 只写运行契约并指向本节。
> **路径写法**：本文路径一律为逻辑路径（不带 `knowledge/`、`archive/` 前缀），并在路径后就近标注头与解析方式——落盘标注「（落 `knowledge/`）」，读取标注「（读 `knowledge/`→`archive/`）」表示先在 `knowledge/` 找、缺失时到 `archive/` 找。归档只改物理位置，逻辑路径不变；新产物只写物理根 `knowledge/`。

## 一、运行入口

体系只有**一个定时任务**：`zslof-timing-trade-1935-signal`（交易日 19:35；非交易日只回执一行）。任务通过 `tushare-data` MCP 确认交易日，并通过体系 MCP `zslof-timing-trade` 计算信号与渲染报告；不查询账户、不下单。

- 运行定义（唯一）：`.pi/mcp-servers/trade-system/zslof_timing_trade/`，含 `mcp_server.py`（实现）、`system.yml`（契约）、`params/`（参数唯一来源）、`templates/`（模板唯一来源）。下文出现的 `params/`、`templates/` 均指该目录下。
- 体系 MCP：注册名 `zslof-timing-trade`，工具与入参见 `交易/交易体系/招商双债LOF择时体系/MCP介绍.md` 与 `trade-system` 技能的 `reference/mcp.md`。
- 参数唯一来源：`params/instrument.json`、`params/timing.json`、`params/runtime.json`。
- 规则唯一来源：`交易/交易体系/招商双债LOF择时体系/择时参数.md`（参数含义、信号与动作协议、状态计数、调参边界）。
- 过程资料与计划的落盘位置以运行定义 `system.yml` 为准。

### 1.1 每日时间轴（交易日）

| 时点 | 事项 | 谁做 |
|:--|:--|:--|
| 15:00 后 | 报当日成交，会话用 `trade-management` 登记并回执 `trade_as_of` | 用户 → 会话 |
| 19:35 | 盘后任务：调体系 MCP 算信号 → 写过程资料 → 渲染报告 → 生成下一交易日计划 → 飞书汇报 | 体系任务 |
| 22:30 | 全局复盘追问：核验成交与持仓、汇总未结 todo | 全局任务 |
| 次日 09:15 | 全局通报：读当日计划 | 全局任务 |
| 次日开盘 | 按计划人工执行（买入 / 全部卖出 / 不操作）；本体系不自动下单 | 用户 |

非交易日：19:35 任务只回执一行，不生成产物。

## 二、盘后任务执行明细（交易日 19:35）

### 2.1 输入与前置

- 交易日判断：`tushare-data.get_trade_calendar`；非交易日发送一行状态后结束。
- 行情：取规则所需区间的日线（回看窗口见 `params/runtime.json#history_lookback_calendar_days`），按 `trade_date` 升序。
- 理论状态：读取**最近先前过程日的 `strategy_state.json`**（`state_lookup = latest_prior_process_date`，禁止读取未来日期状态）：`交易/过程资料/<YYYY-MM-DD>/招商双债LOF择时体系/strategy_state.json`（读 `knowledge/`→`archive/`；两处都有时以 `knowledge/` 为准），并在产物记录 `source_state`（逻辑路径）与 `source_state_detail`（实际位置与来源日期）；找不到时按初始空仓状态推进并在产物标注 `state_source = null`。
- 双头优先级口径（2026-10-17 用户确认）：跨日状态解析一律取「`knowledge/` 优先、`archive/` 兜底」并把实际来源记入产物；**不**套用 `logic-path` 对通用引用的 `duplicate` 报告语义（`knowledge-management/reference/path-protocol.md` 第 4 节）。理由：状态是逐日推进的同一对象，归档只改物理位置，读取端必须给出唯一结果才能继续推进；两处同时存在属归档残留情形，以现存位置为准并留痕即可追溯。
- 参数：运行定义 `params/timing.json`（确认天数、止损/追回开关、计划金额、信号与执行时点）。
- 参数校验：调用前先用体系 MCP 的 `validate_parameters` 校验；失败时记录错误并停止。

### 2.2 步骤与产物

写入目录：`交易/过程资料/<YYYY-MM-DD>/招商双债LOF择时体系/`（落 `knowledge/`；文件名见 `params/runtime.json`）。

| # | 步骤 | 数据来源 | 产物 |
|:--|:--|:--|:--|
| 1 | 取行情（日线，含成交量） | `tushare-data.get_fund_daily`（体系 MCP 内部取数） | — |
| 2 | 推进理论状态（peak / trough / 计数 / 锚）并判定当日信号 | `zslof-timing-trade.calculate(operation="signal", date="{date}")`；状态从最近先前过程日读取（双头解析：`knowledge/` 优先、`archive/` 兜底） | `strategy_state.json`、`signal_facts.json` |
| 3 | 渲染可读信号报告（当日信号、判定依据、锚点与次日关键位） | `zslof-timing-trade.render(artifact="signal_report", date="{date}")`（不传 `document` 时读同日 `signal_facts.json`） | `signal_report.md` |
| 4 | 生成下一交易日唯一正式计划（结构见 2.4） | 上列产物 + 运行定义 `params/timing.json` | `交易/交易计划/<下一交易日>/招商双债LOF择时体系_交易计划.md`（落 `knowledge/`） |
| 5 | 飞书汇报（要点见 2.5） | — | 简报 `摘要/.abstract/<YYYY-MM-DD>_zslof-timing-trade-1935-signal.txt`（落 `knowledge/`） |

步骤 2–3 一律通过体系 MCP 完成；历史脚本已退役（能力由 MCP 同等实现，可在 git 历史中查阅）。需要复核状态推进时用 `replay_check`：从 `params/runtime.json#state_anchor_date` 重放收盘价序列并与存储状态比对（只读，不写产物）。

### 2.3 判定口径

| 判定 | 依据 |
|:--|:--|
| 信号与动作枚举（`buy` / `sell` / `stop_loss_sell` / `chase_buy` / `null`；`buy` / `sell_all` / `hold` / `no_action`） | `交易/交易体系/招商双债LOF择时体系/择时参数.md`「信号与动作协议」 |
| 计数与优先级（持仓 `no_high_days`、空仓 `no_low_days`；止损优先于普通卖出；追回只在理论空仓检查） | `交易/交易体系/招商双债LOF择时体系/择时参数.md`「状态计数」 |
| 参数含义与调参边界 | `交易/交易体系/招商双债LOF择时体系/择时参数.md`「主要参数」「调参边界」，数值读 `params/timing.json` |

本节不复制计数规则与参数数值。

### 2.4 计划结构

标的、方向（买入 / 全部卖出 / 不操作）、计划金额、执行时点（下一交易日开盘）、失效条件（当日收盘已改变判据则计划作废、次日重算）。

- 计划金额读 `params/timing.json#order_amount`，文档中使用「计划金额」这一术语，不从上一日文档复制。
- 卖出动作使用 `sell_all`；不把理论状态写成实际成交。

### 2.5 汇报要点

首行一行式状态；正文列当日收盘与计数变化、`signal` 与 `next_trading_action`、次日关键位、待确认项；不超过 5 行，异常与待办各占一行。

### 2.6 异常分支

| 情形 | 处理 |
|:--|:--|
| 非交易日 | 一行状态回执后结束，不生成产物 |
| 行情缺失或参数无效 | MCP 返回错误时记录失败阶段与错误信息，不生成计划；不编造价格 |
| 最近先前状态缺失或已归档 | MCP 按同一逻辑路径到 `archive/` 解析读取并标注来源位置；仍缺失时按初始空仓状态推进并在产物标注（`state_source = null`） |
| 可用现金 < 计划金额 | 计划照常生成，但标注差异并把金额口径列为待确认项（见 6.1），不改变信号判定 |

## 三、执行与复盘衔接

- **本体系无人工审批环节**：机械信号直接形成下一交易日计划，用户按计划在开盘执行或不下单。
- 成交登记：交易日 15:00 后由用户告知会话，会话用 `trade-management` 登记并回执 `trade_as_of`。
- 复盘：本体系暂不设体系级复盘文件；当日执行情况与偏差由会话记入当日 `交易/交易复盘/<日期>/整体复盘.md`（落 `knowledge/`），22:30 全局任务只核事实与提问。
- 理论状态与实际账户分离：`strategy_state.json` 是理论仓位，实际成交、持仓、手续费与盈亏以 `trade-management` 为准。

## 四、边界

- 只生成信号与计划：不查询账户、不下单、不改参数、不把理论状态写成实际成交。
- 计划金额按 `交易/交易体系/招商双债LOF择时体系/择时参数.md` 的规范渲染，取自当日有效参数。
- 数据或参数无效时记录链路异常并停止，不编造价格或信号。
- 状态推进与信号判定只由体系 MCP 完成；不手工改写 `strategy_state.json`（需要修正时按第七节变更链处理并留痕）。

## 六、按需链

### 6.1 金额口径（未决）

- 现状：计划金额读 `params/timing.json#order_amount`；**体系现金不在文档记录**，执行前用 `trade-management` 当场查：余额用 `cash_balance`／`portfolio_snapshot`，逐笔流水用 `cash_list`／`trade_list`，并同时取 `trade_as_of` 确认是否已登记到最近成交。
- 待裁定（`T-2026-10-16-12`）：按名义 `order_amount` 执行，还是按可用现金取较小者；核对基准是上一步查得的可用现金。
- 裁定前：触发买入而可用现金小于计划金额时，计划标注差异并保留待确认项，不跳过信号判定。

### 6.2 参数调整

调整 `confirmation_days`、止损/追回开关或 `order_amount` 时按第七节执行；参数位置是运行定义 `params/timing.json`；`order_amount` 变更前用 `trade-management` 查得的可用现金与流水核对，不把余额写入本文档。

## 七、变更链

1. 改运行定义的 `params/`、`mcp_server.py`（实现）或 `交易/交易体系/招商双债LOF择时体系/择时参数.md`；
2. 校验：调体系 MCP `validate_parameters`；参数或实现变更后用 `replay_check` 从锚日重放比对存储状态，并核对 `order_amount` 与 `trade-management` 查得的可用现金；
3. 写 `更新日志/<YYYY-MM-DD>_<主题>.md`，记动因、变更、验证与遗留；
4. 同步文档：`交易/交易体系/招商双债LOF择时体系/择时参数.md`、本 SOP、运行定义 `system.yml` 契约说明、`交易/交易体系/招商双债LOF择时体系/MCP介绍.md`；
5. 若改动本 SOP 的章节结构，检查引用它的任务 prompt 是否仍指向正确章节；
6. 告知用户新参数自下一交易日生效；
7. 变更后首个交易日复核实际产物。
