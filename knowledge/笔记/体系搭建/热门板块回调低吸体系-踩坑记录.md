# 热门板块回调低吸体系 · 踩坑记录

> 本文档沉淀体系运行中踩过的坑与教训（Pipeline 陷阱、脚本边界、冷启动模式、数据时效），避免重蹈覆辙。

## 当前架构说明（2026-08-10）

下文出现的 `stock_picker.py`、`buy_signal.py`、`sell_signal.py`、`output/` 和旧参数文件名均是**历史事件发生时的真实上下文**，不得据此调用当前系统。

当前运行入口是体系 MCP `hot-sector-pullback-system`（`calculate` 的四段事实 + `render`），知识库内的脚本已退役，不作为入口；新过程资料写入按日期组织的体系目录。风控由 `risk_signal` 统一计算开盘信号、审慎标签、MA5、MA10 和固定止损，历史章节中“需手动补算 MA10”的描述不再适用于当前流程。

## 一、Pipeline 链式依赖陷阱

### 陷阱 I：非交易日断链（2026-06-19）

**问题复现：** 2026-06-19（周五）被 `is_trading_day.py` 判定为 NON_TRADING_DAY。18:25 执行和 18:30 复盘按规则跳过是正确的（确实无计划可执行），但**18:35 生成计划也因"非交易日跳过"而没有给 06-22（周一）生成计划**。结果：本周一开盘没有交易计划。

**根因：** 三个 cron 的 prompt 统一检查"今天是否是交易日"，但生成计划（generate-plan）的职责是**为下一个交易日做计划**，不是执行今天的事。当今天是非交易日时，仍然需要生成下一个交易日的计划。

**修复方案：**

| cron | 交易日检查 | 原因 |
|------|-----------|------|
| 18:25 回放执行 | ✅ 必须检查 | 执行今天的计划，非交易日无计划可执行 |
| 18:30 复盘 | ✅ 必须检查 | 复盘的目的是评估今日执行质量 |
| **18:35 生成计划** | **❌ 不应检查** | 职责是准备下一个交易日，不管今天是不是交易日，都得为明天准备 |

**具体修改：** 18:35 generate-plan 的 prompt 应**移除第1步的交易日判断**（`is_trading_day.py`），改为**直接运行**。其他步骤中依赖今天日期的逻辑可以保留——有就有，没有就跳过。核心是：**不要因为今天非交易日就跳过生成下一个交易日的计划。**

### 陷阱 II：复盘止损建议因无信号被吞（2026-06-18）

**问题复现：** 2026-06-18 复盘明确建议"威尔泰：明日开盘止损（MA5 已破、买入逻辑已失效）"。但 06-19（周五，非交易日）和 06-22（周一，**交易日**）均未生成该体系的交易计划，导致止损建议从未转化为可执行的交易指令。威尔泰以 -13.59% 继续持有（距 -15% 心理止损线仅 1.4%），这是有实际财务后果的流程失效。

**问题根因（不同于非交易日断链）：**
- 06-22 是交易日，但 generate-plan 仍然没有生成计划
- 最可能原因：**buy_signal.json 输出 signals=0 → generate-plan 判断"无信号→无需生成计划"**，跳过了检查最新复盘是否有 pending 止损建议
- 即：②复盘（18:30）→ ③生成计划（18:35）之间缺失了一个「止损建议转计划」的强制管道

**修复方案（generate-plan prompt 必须包含）：**

```text
步骤A：读取最新复盘文档
  交易/交易复盘/{上一个交易日}/热门板块回调低吸体系_复盘.md

步骤B：解析「下一交易日关注」区块
  查找以下关键词触发动作：
  - 「止损」→ 计划中标注"卖出（止损）"
  - 「开盘止损」→ 计划中标注"卖出（止损）"，执行价=开盘价
  - 「卖出」→ 计划中标注"卖出"
  - 「持有」→ 计划中标注"持有不动"
  - 「观察」→ 计划中标注"盘中关注"

步骤C：强制生成交易计划（每天必须落盘，无例外）
  - buy_signal 有信号 + 无持仓 → 检查回调深度 → 深度够则买入计划，不够则不操作
  - buy_signal 有信号 + 有持仓 → 生成买入+持有/调仓计划
  - 复盘有止损/卖出建议 → 强制生成卖出计划（即使 buy_signal=0）
  - 当前有持仓 → 强制生成持有/卖出计划（持仓不能无主）
  - **无信号 + 无持仓** → **出不操作说明**（解释为什么不开仓：市场环境如何、候选股质量、买入条件未触发的原因）
  - **有热门板块 + 有信号 + 但回调深度不足** → **出不操作说明**（说明板块已热但买点未到，标注观察清单供次日回放执行）
```

**验证方法：** 每个交易日检查：
1. `交易/交易计划/{下一交易日}/` 下**必须**有该体系的计划文件，文件名为 `热门板块回调低吸体系_交易计划.md`
2. 计划文件中包含持仓标的的处理指令（如有持仓）或不操作说明（如无持仓）
3. 复盘文档中的止损建议被反映在计划中

**关键记忆点：** **每天必须有交易计划**——无论是否有持仓、无论是否有信号。有持仓出持有/卖出计划，无持仓出不操作说明。让人看到的是"系统分析过了，决定不操作"，而不是"系统跳过了没管"。**无计划 = 止损建议被丢失 = 真实亏损。**

### 陷阱 III：sell_signal 脚本 vs 复盘定性判断冲突（2026-07-02）

**场景（2026-07-02 实测）：** sell_signal.py 输出士兰微 sell（MA5 首日跌破），但同日复盘文档建议"MA5连续3日不站回→减半仓，MA10失守→清仓"——即第1日不卖。脚本和复盘结论冲突。

**正确处理方式：**
- sell_signal.py 是机械规则（破MA5=卖），不区分第1日还是第N日
- 复盘文档是AI的定性判断，结合了市场环境（系统性大跌）、相对强弱（士兰微优于板块均值）、利润垫等
- generate-plan 应同时读取 sell_signal 输出和复盘结论，当二者冲突时，**以复盘定性判断为准**
- 在交易计划的"注意事项"中记录 sell_signal 触碰但被否决的原因

**决策框架：**

| sell_signal | 复盘建议 | 计划动作 |
|:-----------|:---------|:---------|
| sell（MA5首日） | 监测3日 | 持有不动，注明MA5失守第1日 |
| sell（MA5第3日+） | 监测3日 | 按复盘建议执行（此时通常也建议卖了） |
| sell（MA10失守） | 任何 | 优先执行止损，复盘建议通常和脚本一致 |
| hold | 建议卖出 | 按复盘建议执行（复盘有脚本不知道的信息） |

**关键**：sell_signal.py 是参考信号，不是最终指令。generate-plan 的最终决策权在复盘结论。

### 陷阱 IV：sell_signal 脚本可能从非 hermes-trade DB 源读取持仓

**问题发现（2026-06-26 复盘）：** sell_signal.json 的 `date` 字段为 20260618，其中的 `holdings` 数组包含 4 只股票（有研新材、欧莱新材、先导基电、江丰电子），**这些股票在 hermes-trade 数据库中从未出现**。而实际 hermes-trade 数据库记录的是 6 只不同股票（宝明科技、威尔泰、冠城新材、南芯科技、中国西电、士兰微）。

**如何验证：**

```bash
# 查 hermes-trade DB 实际持仓
trade_cli.py list --account-id MNZH --system-id hot_sector_pullback_system

# 查 sell_signal 中的假设持仓
cat 交易/过程资料/{date}/热门板块回调低吸体系/sell_signal.json | python3 -c "import json,sys; d=json.load(sys.stdin); print([h['code'] for h in d.get('holdings',[])])"

# 对比两份清单 —— 如果不匹配，说明 pipeline 断裂
```

**后果：**
- 实际持仓的止损条件从未被评估（因为 sell_signal 不认识它们）
- 复盘报告依赖 sell_signal.json 时得到错误基线和错误结论
- **止损线丢失 = 真实亏损风险**

**根本原因：** sell_signal 脚本的设计是接收外部传入持仓字典（`{ts_code: buy_price}`），但上游调用者（generate-plan 或 1825 execute）可能没有从 hermes-trade DB 获取当前实际持仓，而是从一个过时的候选列表或假设列表中提取。**这是一个上游调用问题，不是 sell_signal 脚本本身的问题。**

**修复方向（上游 pipeline 层面）：**
1. sell_signal 的调用者应当从 `trade_cli.py list | grep 买入 | ...` 获取当前实际持仓
2. 或者在每日 18:25 execute cron 中增加 sell_signal 的自动计算（基于实际持仓）
3. generate-plan 中检查 sell_signal.json 的 `date` 是否与复盘日期匹配

## 二、MA10 硬止损（sell_signal 不覆盖）

`sell_signal.py` 的 `--positions` 参数仅接收 `{ts_code: buy_price}`，其平仓逻辑只基于 **MA5 趋势转弱**（收盘 < MA5）。它**不计算也不判断 MA10**。

但体系的硬止损规则有一条：**MA10 失守 → 立即清仓**（优先级高于 MA5 监测 3 日缓冲）。这意味着 generate-plan 在运行 sell_signal.py 后，**必须额外手动检查每只持仓的 MA10**，不能仅依赖 sell_signal 的输出。

**什么时候触发 MA10 硬止损：**
- sell_signal 输出 sell（MA5 跌破）+ 手动验证 MA10 也跌破 → **MA10 硬止损，次交易日开盘清仓**
- sell_signal 输出 sell（MA5 跌破）+ 手动验证 MA10 未跌破 → MA5 监测 3 日缓冲，不急于卖出
- sell_signal 输出 hold → 无论 MA10 状态如何，按复盘建议处理

**2026-07-03 实测案例：** sell_signal 输出士兰微 sell（MA5 跌破），手动验证发现 MA10=50.02 也被跌破（收盘 47.25），触发 MA10 硬止损 → 07-06 开盘清仓。

MA10 手动检查代码见 `常用代码速查.md` 的「MA10 手动检查」章节。

## 三、冷启动 / 无持仓复盘模式

当体系处于观察阶段（零持仓、零现金、零交易记录），18:30 复盘仍产出完整结论：

1. **跳过执行复盘的常规步骤**（无计划→无执行→跳过）
2. **跳过资产表现复盘**（无持仓）
3. **信号复盘是核心**：
   - 读取最新 `output/buy_signal.json`，提取信号列表
   - 用 tushare `pro.daily(ts_code=..., start_date=review_date, end_date=review_date)` 批量拉信号股当日数据
   - 对比信号日收盘价 vs 复盘日收盘价，计算胜率、平均收益、跑赢大盘比例
   - 输出表格（代码+名称+信号日收盘+复盘日涨跌幅+量比+回撤%）供分析
4. **sell_signal.json 预计算检查**：`output/sell_signal.json` 可能存在基于假设买入价的模拟持仓和盈亏数据。
   - 这些数据是**系统预计算（hypothetical/projected）**，不是实际成交记录
   - 检查 `sell_signal.sell_signals` → 触发止损的假设标的
   - 检查 `sell_signal.holdings` → 持有中的假设标的及其模拟盈亏
   - 注意 `sell_signal.date` 字段可能指向未来日期（脚本采用未来日期命名），不代表真实数据
   - 复盘文档中**必须明确标注**数据来源（"假设持仓"、"模拟盈亏"），避免与真实成交混淆
5. **组合复盘跳过**（无持仓）
6. **体系复盘重点是改进建议**：提醒入金、板块集中度风险、信号有效性跟踪

**关键**：即使零持仓，复盘结论也要通过最终消息输出，供 18:35 generate-plan 的 context_from 读取。18:35 无复盘结论时会静默跳过——所以 18:30 不能 silent。

## 四、output/ 目录文件可能包含过时数据（关键坑位）

`output/` 下的文件（buy_signal.json, sell_signal.json, sector_heat.json 等）是**脚本运行时的快照**，不是实时状态。它们可能：
- 来自上一轮交易迭代（不同的持仓），当前已不再适用
- `date` 字段可能是较早的日期（如 20260618），而今天是 20260622
- `sell_signal.json` 中的 `holdings` 可能是**假设持仓**（基于某个历史时点的买入价），不是当前实际持仓

**验证方法：**

| 文件 | 核对项 | 验证方式 |
|------|--------|----------|
| `buy_signal.json` | `signals` 数组是否为空 | 直接看 |
| `sell_signal.json` | `holdings` 中的股票代码是否都在当前实际持仓中 | 对比 `trade_cli.py list --account-id MNZH --system-id hot_sector_pullback_system` |
| `sector_heat.json` | `date` 是否足够近（≤3天） | 看 `date` 字段 |
| 所有文件 | `date` 字段 | 确认数据新鲜度 |

**⚠️ 如果 sell_signal.json 中的 holdings 不匹配当前实际持仓，不要引用这些数据。** 直接在复盘中说明 "sell_signal.json 的 holdings 为过时假设数据，与当前实际持仓不匹配，不纳入复盘分析"。

**正确信息来源优先级：**
1. ✅ `trade_cli.py list` / `cash_cli.py balance` — 真实成交数据和现金余额
2. ✅ `pro.daily(ts_code=...)` — 真实行情价格
3. ⚠️ `output/sell_signal.json` — 仅当 holdings 中的代码与实际持仓匹配时才可引用
4. ⚠️ `output/buy_signal.json` — 信号分析的主要来源，但注意日期

**复盘输出关键数据区分原则：**

| 数据类型 | 来源 | 标注方式 |
|---------|------|---------|
| **实际成交** | `trade_cli.py list` 查到记录 | 正常描述 |
| **假设/模拟持仓** | `output/sell_signal.json` 中的 holdings | 标注"模拟"、"假设" |
| **信号次日表现** | `output/buy_signal.json` + tushare 真实行情 | 标注"信号验证"、"真实行情" |

**规则**：如果没有 `trade_cli.py list` 查到的任何实际成交记录，所有关于持仓的讨论都必须加"假设"或"模拟"前缀。

## 五、其他坑位

### output/ 目录必须平铺

**不要建子目录！** 用户明确说过"buy signal根本就不需要是一个目录"、"for market candidate.json就可以了"。
- 全量候选命名 `full_market_candidate.json`（不是 `for_market_candidate`，用户纠正过"for"是错的）
- 热门行业候选命名 `hottest_industry_candidate.json`（不是嵌套目录）
- 所有文件命名用下划线，不要多余层级

### 退出监控的单日判定敏感性（2026-08-03 实测）

单日涨跌作为"退出重点监控"依据过于敏感——长城电工 600192 于 7/31 因单日 -1.80%（监控标的中唯一下跌）被移出监控，8/3 即涨停 +10.06%。单日下跌可能是随机波动而非趋势转弱。若计划/复盘提到"退出监控"，执行时不要机械照做，先确认是否基于连续多日表现或技术形态（MA5/MA10 位置）而非单日涨跌；单日依据时在复盘记录为信号偏差即可，不要改执行动作。退出监控 ≠ 不可再入池。

### 预填的执行记录（情况A "持有不动"）

当计划动作为"不操作/空仓持有"时，generate-plan 已在计划文件中预填执行记录行（如 `| 2026-07-13 | 按计划不操作 | — |`）。replay-execute **不要**编辑计划文件添加或修改该行——记录已存在且完整。只需在最终消息和简报中标注"按计划执行"即可。

### 复盘 cron 不要重新扫描涨停/板块热度

`pro.limit_list_d()` / `pro.limit_list()` 无访问权限会直接报错（`抱歉，您没有接口(limit_list_d)访问权限`）。复盘中的"板块热度"直接沿用当日交易计划中的评估结论即可——涨停扫描是 18:35 generate-plan（stock_picker + sector_heat）的职责，不是复盘的。复盘的重点是执行一致性 + 监控标的表现 + 大盘环境，不是重新选股。若确实需要验证板块热度，用 `pro.daily(trade_date=...)` 全市场日线按 `pct_chg >= 9.8` 近似涨停，不依赖 limit_list 系列接口。

### 18:30 复盘不能 silent

**18:30 不能 silent**——18:35 generate-plan 靠 context_from 读复盘结论，silent 会导致下游断链。即使无交易（"无交易，体系正常"）也要输出完整复盘结论（文档 + 精简版推送）。

### stk_mins 限频与开盘段降级（2026-09-27 修复）

**现象**：有持仓时 19:25 `risk_signal.py` 在 `fetch_opening_signal` 处直接 `Exception: 频率超限` 退出 → `risk_signal.json` / `prudent_tags.json` / `state.json` **三者全不产出**。曾被误判为「结构性必然失败、数据取不到」。

**真因**：不是数据取不到，是**脚本缺降级路径**。官方 `stk_mins` 限频实测 **1 次/小时**（同小时重复调用必拒），而 19:00 replay-execute / 19:10 review / 19:25 generate-plan **同处一小时** → 第一处调用吃掉额度，后两处必挂。

**处置**：
1. `risk_signal.py` 加降级链，顺序由 `params/risk.json` 的 `opening_signal.fallback_sources` 控制（默认 `["official","promax"]`）；promax 走 `tushare-proxy` 技能，**必须校验 `trade_time` 日期 == 目标交易日**。
2. 全失败时标 `unavailable` 且**照常产出三个 JSON**，不再整份丢失；`unavailable` 不属利空信号 → 不刷新审慎标签。
3. 输出新增 `data_sources` 字段（每只持仓的实际取数通道），复盘据此判定数据可信度。
4. 参考价 `reference_price` 改用**目标日日线 `open`**（权威定义、`daily` 不限频、与成交价口径一致），不再取分钟首根 open（promax 下实测偏 1.1%）。
