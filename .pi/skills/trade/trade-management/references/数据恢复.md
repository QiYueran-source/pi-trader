# 历史交易数据恢复

> 本文件仅记录旧 Hermes 工作区的历史恢复流程，不属于当前交易数据落盘流程。

当前交易账户、交易流水、现金流水、自选股和盈亏数据，必须通过 `trade-management` MCP 访问。不得直接写 SQLite，不得直接执行 SQL，不得调用旧 CLI。当前数据库位置和表结构由 MCP 及其运行配置管理；本文件中的旧路径、旧数据库名称和旧脚本仅供历史审计，不可作为现行操作指引。

## 历史背景

历史交易记录曾保存在旧 Hermes 工作区的 Markdown 复盘文档中，并曾尝试通过脚本恢复到 SQLite。该流程可能包含账户推算、数量推算、日期推算和批量写入，存在把推测数据写入账本的风险，现已废弃。

## 当前恢复原则

1. 先通过 `trade-management` MCP 查询当前账户、交易和现金事实。
2. 只有用户明确确认的历史成交，才能通过 MCP 的受控写入工具补录。
3. 文档内容只能作为待核对输入，不能据此自动推算数量、价格、成交日期或现金流水。
4. 发现历史数据缺失、重复或无法确认时，停止写入并报告差异，不能直接清空、重建或覆盖账本。
5. 动态知识文档来源字段使用逻辑路径；历史物理路径只按兼容规则读取，不在恢复流程中批量改写。

## 明确废弃的历史做法

以下内容只保留用于识别旧资料，禁止在当前项目执行：

- 直接操作 SQLite 数据库；
- 直接执行 `INSERT`、`DELETE`、`CREATE TABLE` 等 SQL；
- 使用旧的 `account_cli.py`、`trade_cli.py` 或 Hermes CLI；
- 通过总盈亏反推成交数量；
- 通过持有天数推算卖出日期；
- 清空 `trade`、`cash_flow` 或 `account` 表后重建数据。

当前交易管理规则见 `.pi/skills/trade/trade-management/SKILL.md`，所有实际补录必须遵守该技能和 MCP 的确认边界。
