# Pi cronjob 工具使用

## 运行时注册与仓库定义

仓库中的 `cronjob.yml` 和 `prompt.txt` 是可追踪的任务定义。Pi 中通过 `schedule_prompt` 注册的是运行时状态，两者需要保持一致。

任务目录存在不代表任务已经注册；任务已经注册也不代表仓库文件是最新版本。

## 创建流程

创建新任务时：

1. 判断是全局型还是体系型。
2. 创建任务目录和两个核心文件。
3. 校验名称、时间、路径和 prompt。
4. 查询当前注册任务，确认不存在同名任务。
5. 向用户说明任务名称、时间、目的和影响，并获得确认。
6. 使用 `schedule_prompt`（`action: add`）创建任务：传入 `cronjob.yml` 的字段（`name`/`schedule`/`description`/`type` 等；`inline` 模式不传 `model`），以及 `prompt.txt` 的**文本内容**（工具不接受文件路径）。
7. 再次查询，确认注册结果并记录返回的 `job_id`。
8. 核查三件事：`list` 中该任务有 `Next:`；运行时记录不带 `session`；运行时 `prompt` 与 `prompt.txt` 逐字一致。
9. 将 `job_id` 回填到仓库中的 `cronjob.yml`。

不要只在 Pi 中创建而不保存仓库文件，也不要误把 `prompt.txt` 的路径当作注册工具的 prompt 内容；注册工具需要实际的 prompt 文本时，应读取文件内容后传入。

## 查询和检查

定期或开始工作前查询已注册任务，至少核对：

- 任务是否存在。
- 任务名称和 `job_id`。
- schedule 是否与仓库定义一致。
- prompt 是否与仓库文件一致。
- **是否有 `Next`**（没有 `Next` 说明调度器里没有存活定时器，即使磁盘上有记录也不会触发）。
- 运行时记录是否意外带有 `session` 字段（会话绑定，重启后失效）。
- 任务是否因为重启而消失。

检查重点是“是否注册”和“配置是否一致”，不需要建立复杂的运行指标体系。

## 更新流程

低风险的文字、路径或描述修正可以在确认影响后更新；以下变更必须先与用户确认：

- 执行时间或频率。
- 删除、暂停或恢复。
- 切换运行模式（`inline` ↔ `subagent`）：Pi 无法原地清空 `model`，必须 remove + add，`job_id` 会改变，需回填并告知用户。
- 任务类型或所属体系。
- 通知渠道。
- 核心执行逻辑。
- 可能产生交易动作的内容。

确认后：

1. 先更新仓库文件。
2. 查询任务获取当前 `job_id`。
3. 使用 `schedule_prompt` update 更新运行时配置。
4. 如果工具要求传入完整配置，保留原有的依赖或上下文参数。
5. 再次查询确认，并核查 `Next` 是否存在。

## 删除和重命名

删除前必须确认任务名称、删除原因和影响范围。删除时同时处理：

- Pi 中的注册任务。
- 仓库中的任务目录。
- 其他任务或文档中的名称引用。

重命名不能只改目录名，至少同步任务目录、`name`、prompt 中的引用和 Pi 注册名称。

## Pi 重启后的恢复

Pi 重启或调度器状态重置可能造成运行时注册丢失。启动后：

```text
扫描仓库中的任务定义
→ 查询 Pi 当前注册任务
→ 按 name 对比，并检查每项是否有 Next
→ 汇报缺失或不一致
→ 获得确认后重新注册或重挂
```

两种情形区分处理：

- **磁盘有记录但无 `Next`**：用 `update` 逐条重挂，`job_id` 不变。
- **`list` 中完全缺失**：按仓库定义重新注册，并回填新 `job_id`。

两种情形都要顺带检查运行时记录是否带 `session` 字段，有则清除后重挂。

重新注册前先按 `name` 查询，避免同名重复注册。交易体系任务缺失时默认只汇报，不自动恢复，等待用户确认。

## 最小错误汇报

工具操作失败时，汇报：

- 操作类型。
- 任务名称和 `job_id`（如已知）。
- 失败阶段。
- 原始错误原因的简要说明。
- 是否已经改变仓库文件或运行时注册状态。

不自动重试、回滚或删除其他任务，除非用户另行要求。
