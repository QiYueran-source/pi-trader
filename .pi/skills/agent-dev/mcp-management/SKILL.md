# MCP 管理

## 定位

MCP（Model Context Protocol，模型上下文协议）服务通过配置接入外部工具。本技能负责识别配置、检查问题、说明影响和执行用户明确确认的变更，不负责自动运维。

当前项目的 MCP 配置位于：

```text
.pi/mcp.json
```

## 使用范围

适用于：

- 查看当前 MCP 服务及其工具。
- 检查 stdio 或 HTTP 配置。
- 排查服务无法启动、连接失败或工具未发现。
- 新增、修改、停用或删除 MCP 服务。

## 检查顺序

```text
读取配置
→ 检查 command / url
→ 检查脚本路径和参数
→ 检查环境变量名称
→ 确认服务能否启动和连接
→ 确认工具是否被发现
→ 必要时验证工具调用
```

服务配置存在不等于服务连接成功；工具被发现也不等于工具调用正常。报告问题时说明具体失败阶段和原因。

## 人工确认边界

以下操作必须先说明影响并获得用户确认：

- 新增、替换或删除服务。
- 修改 command、args、url、headers 或环境变量。
- 修改具有交易、数据库写入或外部副作用的服务。
- 安装、升级或降级 MCP 依赖。

默认不自动安装、升级、删除或替换 MCP 服务。发现明文密钥时提醒用户，但本技能不负责权限和密钥管理。

## 修改后

配置变更后，根据 Pi 的加载机制重启或重新加载 MCP 客户端，再检查服务连接和工具发现结果。不要只修改文件后就假设运行时已经生效。

## 文件类型与路径边界

本技能只管理 MCP 资产，包括 `.pi/mcp.json`、`.pi/mcp-servers/` 下的服务实现、服务环境变量和工具发现。

MCP 配置中的固定路径通常是服务入口、数据库文件、知识库根目录或归档根目录等静态基础设施路径。不得把某个具体动态知识文件写入长期配置。运行时传入的动态知识路径必须遵守 `knowledge-management` 的逻辑路径协议。

MCP 如果接收、返回或保存动态知识来源路径，应区分逻辑路径和物理路径。

MCP 实现可以在运行时读取和传递具体动态知识逻辑路径，但不能在配置或通用工具契约中写死某个日期的动态知识文件。

## 服务实现结构

服务目录自包含，`mcp_server.py` 只做工具注册与路由。以下为原则，按服务规模取用，不强制：

- 依赖同目录：服务自身的运行定义类文件（参数、模板、契约、静态映射表）与实现放同一目录，不散落到知识库或其它共享目录。
- 凭据不复制：密钥、token 集中放 `.pi/mcp-servers/tushare/.env`（已被 `.gitignore` 忽略），各服务按需读取。
- 动态内容不入目录：服务目录只放静态与运行定义资产，不放知识库文档、过程资料或运行时产物。
- 实现分模块（视规模）：实现有多个独立职责（参数校验、模板渲染、外部数据访问等）时，按职责拆到 `functions/<模块>.py`，并让一个模块集中推导路径常量、其它模块从它取；简单服务保持单文件即可，不做无收益的拆分。
- 拆分验收：函数体逐字搬运、工具契约不变、同一输入复算结果一致。

体系类服务的目录与命名映射（`system-id`、注册键、目录名、任务名）见 `trade-system` 技能 `reference/mcp.md`，本技能不重复定义。

## 管理边界

本技能负责 MCP 的服务配置、连接、工具发现和接口验证；动态知识文档的分类、命名和引用协议由 `knowledge-management` 定义，业务数据库字段的具体语义由对应业务 Skill 定义。

## 失败汇报

只需汇报：服务名称、操作、失败阶段、原因，以及配置或运行时状态是否已经改变。
